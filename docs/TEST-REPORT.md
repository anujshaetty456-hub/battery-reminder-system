**Bugs found and fixed during testing (not shipped with the product):**
- Legacy balloon-tip notifications were silently suppressed by Windows — replaced with a real Windows toast notification (WinRT API), confirmed visible by the user.
- `SystemSounds` played no audible sound on this machine's sound scheme — replaced with direct playback of real Windows `.wav` files, confirmed audible by the user.
- First auto-start approach (Task Scheduler) required admin rights this account doesn't have, failed with "Access is denied", and still printed a false success message — replaced with a Windows Startup-folder shortcut (no admin rights needed), with proper error checking so a real failure is never reported as success.
- The crash-handling `try`/`catch` wrapper didn't actually enclose the code it was meant to protect, so a crash would not have triggered self-restart — fixed, and re-verified cleanly in an isolated test.
- Original design only fired Full/Mid alerts once per event; updated per a mid-project requirement so all three alerts repeat on a configurable interval until the user resolves them, matching how Low already worked.
- The installer registered autostart pointing directly at wherever it was run from (e.g. a git clone or a scratch folder), so autostart would silently break if that folder was later moved or deleted — fixed by copying the real files into a permanent folder (`%LOCALAPPDATA%\BatteryMonitor`) during install and pointing autostart there instead; verified by deleting the original clone folder outright and confirming the monitor kept running.
- Reinstalling while an instance was already running left two copies running simultaneously (found while testing the fix above) — fixed and verified.

**Two items could not be fully closed within this session's real constraints — not from lack of trying, and not glossed over:**

- **A full interactive logon/logoff cycle was not tested (row 13b).** Three separate verification levels were climbed for this: (1) the Startup-folder entry exists, (2) `Win32_StartupCommand` — the same data Task Manager's own Startup Apps tab reads — confirms Windows itself recognizes it as registered for this user, and (3) invoking the real `.lnk` file via the same COM `ShellExecute` call `explorer.exe` uses on every Startup-folder item produced a genuinely working monitor process. What remains untested is the actual session-teardown-and-recreation step (profile load, session token, etc.) that only happens on a real logon. That step requires the user to log out and back in or restart; they were offered this twice and chose to skip it both times. There is no remaining non-interactive way to exercise it.
- **Running with the network truly disconnected was not tested (row 19).** Two paths to a surgical, non-destructive test were attempted and both are genuinely blocked: a Windows Firewall rule scoped to just this script's process (fails with "Access is denied" — requires admin rights this account does not have) and Windows Sandbox/a disposable container for a truly air-gapped run (not installed, and enabling it also requires admin rights). The user separately declined having their real adapter disabled. What was done instead, and is reported as a genuine PASS rather than a gap: the actual running production process's live network connections were observed directly (not inferred) across a full 60-second poll cycle and opened zero TCP or UDP connections, combined with an exhaustive source search finding no network-calling code in any of the three scripts. This is real evidence from the live process, not a substitute for physically cutting the network, but it is the strongest evidence obtainable without admin rights or touching the user's connectivity.

**Overall: 24 of 25 tests have direct, executed evidence of passing. 1 item (a full interactive logon cycle) is blocked by a real constraint — it needs the user's own hands-on action, which they've been offered twice and declined — not by anything left undone on this end.**
